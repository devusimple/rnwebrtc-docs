01

What it is, and what it isn't

react-native-webrtc is a native module that bridges the browser's WebRTC APIs into React Native. It gives you RTCPeerConnection, RTCIceCandidate, RTCSessionDescription, mediaDevices, and an RTCView component for rendering a video stream — the same shapes you'd use in web WebRTC, ported to iOS and Android via native code.

It does not include a signaling server. WebRTC handles the media transport once two peers agree to connect, but the initial "here's who I am and how to reach me" exchange is left entirely up to you — usually over a WebSocket or an existing backend.

Platform support (per official repo): Android and iOS are fully supported (audio/video + data channels, WebRTC M124, Unified Plan only since v106). tvOS supports audio/video only. macOS is not actively supported, Windows is not supported. Expo works via expo-dev-client + @config-plugins/react-native-webrtc — never Expo Go. See the Expo end-to-end example.

Both iOS and Android need a bit of native config after the package install:

  • iOS: CocoaPods 1.10+, platform :ios, '12.0' or higher, run pod install, and add camera/microphone usage descriptions (NSCameraUsageDescription, NSMicrophoneUsageDescription) to Info.plist.
  • Android: API level 24+, add CAMERA, RECORD_AUDIO, MODIFY_AUDIO_SETTINGS, ACCESS_NETWORK_STATE, CHANGE_NETWORK_STATE, and INTERNET to AndroidManifest.xml (plus BLUETOOTH* for BT devices), enable Java 8 support, and request the runtime permissions before calling getUserMedia.

Expo managed workflow? The @config-plugins/react-native-webrtc plugin handles the manifest/plist, minSdk 24, and desugaring flag for you — see the Expo end-to-end example.

03

The handshake, in plain terms

Every WebRTC connection — video, audio, or plain data — goes through the same offer/answer dance before any media flows. This part trips people up more than the code does, so it's worth having straight before you write anything.

Caller creates an RTCPeerConnection, generates an offer (a description of the media/data it wants to send), and sends that offer to the callee — through your own signaling channel, not WebRTC.
Callee receives the offer, sets it as the remote description, generates an answer, and sends it back — again over your signaling channel.
Both sides exchange ICE candidates as they're discovered — each candidate is a possible network path (local IP, router-mapped IP via STUN, or a relay via TURN).
Connection once a working candidate pair is found, the peer connection fires connectionState: "connected" and media/data starts flowing directly between devices.

Everything in the first three rows is signaling — plumbing you own. Only the last row is WebRTC itself.

04

A minimal signaling exchange

You can use anything that can pass messages between two clients — a WebSocket server is the common choice. Here's the client side of that exchange, assuming a socket object with emit/on, sitting on top of a peer connection. 

signaling.tsimport {
  RTCPeerConnection,
  RTCIceCandidate,
  RTCSessionDescription,
} from 'react-native-webrtc';

const configuration = {
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    // add a TURN server for connections behind restrictive NATs
  ],
};

const pc = new RTCPeerConnection(configuration);

// outgoing ICE candidates: forward each one over your signaling channel
pc.onicecandidate = (event) => {
  if (event.candidate) {
    socket.emit('ice-candidate', event.candidate);
  }
};

// caller: start the offer
async function startCall() {
  const offer = await pc.createOffer({
    offerToReceiveAudio: true,
    offerToReceiveVideo: true,
  });
  await pc.setLocalDescription(offer);
  socket.emit('offer', offer);
}

// callee: respond to an incoming offer
socket.on('offer', async (offer) => {
  await pc.setRemoteDescription(new RTCSessionDescription(offer));
  const answer = await pc.createAnswer();
  await pc.setLocalDescription(answer);
  socket.emit('answer', answer);
});

// caller: accept the answer
socket.on('answer', async (answer) => {
  await pc.setRemoteDescription(new RTCSessionDescription(answer));
});

// both sides: apply incoming candidates
// if remoteDescription isn't set yet, queue them (see CallGuide step 5)
socket.on('ice-candidate', async (candidate) => {
  await pc.addIceCandidate(new RTCIceCandidate(candidate));
});

Per the official CallGuide, candidates arriving before setRemoteDescription should be queued in an array and flushed after — otherwise the handshake can stall on slow networks.

05

A video call, end to end

Grabbing the camera and attaching it happens through mediaDevices.getUserMedia, same shape as on the web. Add the resulting tracks to the peer connection before you create the offer.

VideoCallScreen.tsximport { useEffect, useRef, useState } from 'react';
import { RTCView, mediaDevices, MediaStream } from 'react-native-webrtc';

function VideoCallScreen({ pc }) {
  const [localStream, setLocalStream] = useState<MediaStream | null>(null);
  const [remoteStream, setRemoteStream] = useState<MediaStream | null>(null);

  useEffect(() => {
    async function setup() {
      const stream = await mediaDevices.getUserMedia({
        audio: true,
        video: { frameRate: 30, facingMode: 'user' },
      });
      setLocalStream(stream);
      stream.getTracks().forEach((track) => pc.addTrack(track, stream));
    }
    setup();

    pc.ontrack = (event) => {
      setRemoteStream(event.streams[0]);
    };

    return () => { pc.ontrack = null; };
  }, [pc]);

  return (
    <>
      {remoteStream && (
        <RTCView streamURL={remoteStream.toURL()} style={styles.remote} />
      )}
      {localStream && (
        <RTCView streamURL={localStream.toURL()} style={styles.local} objectFit="cover" mirror />
      )}
    </>
  );
}

Both RTCView instances read from a MediaStream via .toURL() — it's not a real URL, just how the native view gets pointed at the right stream.

06

Data channels, without any media

If you just want to move bytes between two devices — file transfer, game state, chat — you don't need getUserMedia at all. A RTCDataChannel rides over the same peer connection and the same offer/answer/ICE handshake shown above. 

dataChannel.ts// caller creates the channel before making the offer
const channel = pc.createDataChannel('file-transfer', {
  ordered: true,
});

channel.onopen = () => {
  channel.send('hello from the caller');
};

channel.onmessage = (event) => {
  console.log('received:', event.data);
};

// callee: the channel arrives on the peer connection, not created manually
pc.ondatachannel = (event) => {
  const receiveChannel = event.channel;
  receiveChannel.onmessage = (e) => console.log('got:', e.data);
};

For binary payloads — like file chunks — send ArrayBuffers and set channel.binaryType = 'arraybuffer'. Chunk large files (64KB is a safe default) and reassemble on the other end; data channels don't guarantee a message-size ceiling across all platforms. Full demo: file-sharing app →

07

Cleanup

Peer connections and media tracks don't get garbage collected for free — leaving them open drains battery and holds the camera/mic open. Tear down explicitly when a call ends or a screen unmounts.

teardown.tsfunction endCall(pc, localStream) {
  localStream?.getTracks().forEach((track) => track.stop());
  pc.close();
}

Do this in a useEffect cleanup function so it fires on unmount, not just on an explicit "hang up" button.

Things that bite people

Issue What's actually going on
getUserMedia hangs or rejects Runtime permission wasn't granted before the call — request camera/mic permission explicitly on Android first.
Connects on wifi, fails on cellular No TURN server configured — STUN alone can't traverse symmetric NATs, which are common on carrier networks.
Works in Expo Go, then doesn't It never did — this module has native code and needs a custom dev client, not Expo Go.
Black remote video Usually ontrack firing before the component listening for it has mounted — buffer the stream in state, not a ref checked once.
